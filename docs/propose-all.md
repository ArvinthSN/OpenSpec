# Batch Proposals: `/opsx:propose-all`

The `/opsx:propose-all` command generates multiple OpenSpec proposals from a single requirement-analysis and planning document in one execution.

---

## Why It Exists

When planning large projects or multi-capability systems, you often have a comprehensive requirement analysis document (such as `OpenSpec_Requirement_Analysis_and_Planning.md` or a PRD generated by the `requirement-to-openspec` skill).

Generating proposals one-by-one with `/opsx:propose <name>` for 5, 10, or 20 specifications is repetitive and prone to missing cross-specification dependencies.

`/opsx:propose-all` solves this by:
1. Analyzing the entire requirement document in one pass.
2. Dynamically discovering all proposed specifications and their prompts.
3. Performing dependency analysis and topological ordering.
4. Enforcing a **mandatory review and approval gate** before anything is created.
5. Batch-creating independent OpenSpec changes in topological order.
6. Validating all artifacts and reporting consolidated results.

---

## How It Differs From `/opsx:propose`

| Feature | `/opsx:propose` | `/opsx:propose-all` |
|---|---|---|
| **Scope** | Single change | Multiple changes in batch |
| **Input** | Short description or change name | Full requirement analysis / planning document |
| **Dependencies** | Individual change focus | Cross-change dependency ordering & topological sequence |
| **Approval** | Immediate creation of one change | Mandatory proposal plan review & explicit confirmation gate |
| **Output** | `openspec/changes/<change-name>/` | Multiple `openspec/changes/<change-name>/` directories |

---

## Input Document

### Default Document

By default, `/opsx:propose-all` searches for:
```text
OpenSpec_Requirement_Analysis_and_Planning.md
```
in the project root or current working directory.

### Fallback Locations

If the default file is not found, it checks:
- `openspec/planning.md`
- `planning.md`

If neither exists, the command asks you to provide the path:
> "Could not find `OpenSpec_Requirement_Analysis_and_Planning.md`. Please provide the path to your requirement-analysis or planning document:"

### Custom Document Path

You can pass an explicit document path as an argument:
```text
/opsx:propose-all path/to/my-requirements.md
```

## The Workflow Step-by-Step

### 1. Document Reading and Analysis

The command reads the complete document (not just headings) and extracts:
- **Project Goals & Architecture**: Technical constraints, frameworks, and architecture.
- **Specifications**: All proposed changes (whether 2, 5, 10, or 20+).
- **Proposal Prompts**: The exact prompt text written for each proposal.
- **Requirements Covered**: Mappings between specifications and functional/non-functional requirements.
- **Dependencies**: Prerequisites for each specification.

### 2. Consolidated Proposal Plan

Before creating any files, the AI formats a comprehensive plan:
- **Project Summary**: Architecture and scope.
- **Specification Inventory**: Table of specifications, purpose, requirements, and dependencies.
- **Proposal Prompt Inventory**: Exact prompts that will be executed for each specification.
- **Dependency Analysis**: Independent specifications vs. ordered dependent specifications.
- **Validation**: Coverage check ensuring all requirements are covered and no circular dependencies exist.

### 3. Mandatory Review and Approval Gate

The workflow **strictly halts** and requests explicit confirmation. You are presented with four options:

- **Option 1 — Approve All**: Approves the plan and proceeds to create all proposals in dependency order.
- **Option 2 — Modify**: Request adjustments to specification names, scope, prompts, dependencies, or ordering. The plan is updated and presented again for approval.
- **Option 3 — Exclude Specifications**: Select specifications to omit. The AI re-evaluates dependency impacts on remaining specifications and asks for confirmation.
- **Option 4 — Cancel**: Aborts the workflow without making any changes.

> [!IMPORTANT]
> No proposals or files are created before you provide explicit approval.

### 4. Sequential Batch Generation

Upon approval, the AI generates each approved specification as an **independent change directory**:
- `openspec/changes/<spec-1>/`
- `openspec/changes/<spec-2>/`
- `openspec/changes/<spec-3>/`

For each specification:
1. Runs `openspec new change "<name>"`.
2. Resolves artifact order closing over `applyRequires` and `requires` edges.
3. Generates all required schema artifacts (`proposal.md`, `specs/`, `design.md`, `tasks.md`).
4. Validates each change with `openspec validate "<name>"`.

### 5. Conflict Handling and Failure Recovery

- **Existing Changes**: If a change with the same name already exists, the AI alerts you rather than silently overwriting it.
- **Partial Executions**: Can safely resume without duplicating already completed proposals.
- **Failure Isolation**: If one specification fails to generate or validate, dependent downstream specifications are marked `Skipped (blocked by dependency)`, while remaining independent specifications continue processing safely.

### 6. Consolidated Execution Report

Once finished, a final execution report is displayed with metrics and next steps:

```text
## OpenSpec Batch Proposal Results

Total identified: 3 | Approved: 3 | Successfully created: 3 | Failed: 0 | Skipped: 0

| # | Specification | Status | Change Name | Location |
|---|---|---|---|---|
| 1 | identity-and-access | Validated | identity-and-access | openspec/changes/identity-and-access/ |
| 2 | customer-profile | Validated | customer-profile | openspec/changes/customer-profile/ |
| 3 | billing-subscription | Validated | billing-subscription | openspec/changes/billing-subscription/ |

All approved proposal artifacts are ready. When you are ready to implement a change, run /opsx:apply <change-name>.
```

---

## How to Enable

`/opsx:propose-all` is available in the expanded workflow set. To enable it in your project:

1. Configure your workflow profile:
   ```bash
   openspec config profile
   ```
   Select `custom`, and ensure `propose-all` is checked.

2. Apply to your project:
   ```bash
   openspec update
   ```
